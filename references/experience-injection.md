# 经验注入指南

## 核心原则

1. **经验不可凭空编造**：区分度和边界意识依赖用户真实经验
2. **主动追问缺失信息**：用户往往只给一句话，需要追问具体细节
3. **经验可拆分注入**：同一段经验可以注入到回答的多个位置
4. **诚实标注来源**：明确区分"实战经验"和"理论推测"

---

## 经验提取流程

### Step 1: 接收经验素材

用户可能提供的格式：
- 一句话描述："我之前做过 RAG 的 chunking 优化"
- 一段话："在项目中我们发现 512 token 的 chunk 效果不好，后来改成了 256 + overlap"
- 一篇文章/笔记：完整的复盘文档

### Step 2: 评估素材完整度

检查是否包含以下要素：

| 要素 | 说明 | 追问示例 |
|------|------|---------|
| 场景背景 | 什么项目、什么阶段、什么问题 | "这是在什么业务场景下做的？" |
| 具体动作 | 做了什么决策、改了什么 | "具体做了哪些调整？" |
| 量化结果 | 数字、指标变化 | "效果提升了多少？有具体数字吗？" |
| 失败经历 | 踩过的坑、和预期不符的地方 | "有没有试过但失败的方法？" |
| 边界条件 | 什么条件下适用/不适用 | "这个方案在什么情况下会失效？" |
| 事后反思 | 如果重来会怎么做 | "如果重新做，你会改变什么？" |

### Step 3: 主动追问

如果素材不完整，**必须追问**。追问示例：

```
你提到做过 chunking 优化，我想了解更多细节：

1. 具体场景：是什么业务？数据量大概多大？
2. 量化结果：召回率/准确率提升了多少？有具体数字吗？
3. 失败经历：有没有试过但效果不好的方案？
4. 边界条件：这个方案在什么情况下可能不适用？

这些信息能帮我更好地把你的经验注入到相关题目中。
```

### Step 4: 整理结构化素材

将用户回答整理成以下格式：

```markdown
## 经验素材：{{经验标题}}

### 场景背景
- 项目：...
- 阶段：...
- 问题：...

### 具体动作
- 决策：...
- 实施：...

### 量化结果
- 指标变化：...
- 对比数据：...

### 失败经历
- 尝试过但失败的方法：...
- 和预期不符的地方：...

### 边界条件
- 适用条件：...
- 不适用条件：...

### 事后反思
- 如果重来会怎么做：...
```

## 经验匹配流程

### Step 1: 搜索相关题目

在 Obsidian 中搜索与经验相关的题目：

```bash
obsidian search query="{{关键词}}" limit=20
```

### Step 2: 评估匹配度

| 匹配度 | 说明 | 处理方式 |
|--------|------|---------|
| 强匹配 | 经验直接回答了题目中的某个子问题 | 注入到题目笔记 |
| 弱匹配 | 经验与题目相关但不是直接回答 | 创建关联链接 |
| 无匹配 | 没有找到相关题目 | 告知用户，建议创建独立经验笔记 |

### Step 3: 确定注入位置

一段经验可以注入到回答的多个位置：

| 注入位置 | 适合的经验类型 | 示例 |
|---------|--------------|------|
| 具体方案 | 具体的实施方法、工具、参数 | "我们用的是 256 token + 50 token overlap" |
| 洞察力 | 反直觉观察、跨领域连接 | "很多人以为 chunk 越大越好，但我们发现..." |
| Trade-off | 方案代价、失效条件 | "这个方案的问题是增加了 30% 的存储成本" |
| 区分度 | 个人叙事、项目背景 | "在 XX 项目中，我们遇到了..." |
| 失败案例 | 踩坑经历 | "我们一开始试过 1024 token，结果发现..." |

### Step 4: 展示注入方案

向用户展示注入方案，确认后再写入：

```
我找到了以下相关题目：

1. [[RAG Chunking 策略设计]] - 强匹配
   注入位置：
   - 具体方案：你的 chunking 参数设置
   - 洞察力：chunk 大小与召回率的非线性关系
   - Trade-off：overlap 带来的存储成本

2. [[向量检索召回优化]] - 弱匹配
   注入位置：
   - 关联链接：在"延伸阅读"中添加

是否确认注入？如有调整请告诉我。
```

## 注入时的注意事项

### 1. 保持原文结构

注入经验时，不要破坏原有回答的结构。经验应该作为**补充**，而非重写。

### 2. 明确标注来源

```markdown
### Step 2: 参数调优

...（原有内容）

> **实战经验**：在电商搜索项目中，我们发现 512 token 的 chunk 在长 query 场景下召回率明显下降，最终采用 256 token + 50 token overlap，召回率从 62% 提升到 89%。
```

### 3. 区分"实战经验"和"理论推测"

```markdown
> **实战经验**：...（来自用户真实项目）

> **理论推测**：...（基于原理推导，未经验证）
```

### 4. 保留失败经历

失败经历是边界意识的重要来源，不要删除：

```markdown
> **踩坑记录**：我们一开始试过 1024 token 的 chunk，以为更大的上下文会更好，结果发现召回率反而下降了 15%。原因是长 chunk 导致边界信息被稀释。
```

## 无匹配题目时的处理

如果没有找到相关题目：

```
我在你的 Obsidian 中没有找到与这段经验直接相关的题目。

建议：
1. 创建独立的经验笔记，存放在 `02-经验/` 目录
2. 等后续有相关题目时再注入

是否创建独立经验笔记？
```
